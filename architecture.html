3. Data Layer — Entity Mapping

All entities reside in a single NeonDB (PostgreSQL) database. For a 100–500 user scale in year one, a monolithic schema in one database is correct — no partitioning, sharding, or separate read replicas are needed at this stage.

Timezone convention: All timestamps stored as TIMESTAMPTZ (UTC) in PostgreSQL. The API layer converts to the user's local timezone when returning leaderboard daily/weekly boundaries and admin reports. This is stated explicitly in requirements.json and must be enforced in every query that involves time-bounded aggregation.

4. Architectural Rationale

4.1 Monolith over microservices

requirements.json sets a 1-week v1 target with a small/agent-led team and a budget of "minimise cost." A single FastAPI application with modular routers (auth, game, leaderboard, IAP, ads, analytics, admin) is the correct choice. A microservice topology would require container orchestration, service discovery, and inter-service auth that cannot be stood up and debugged in one week by a small team. Microservices can be extracted later if specific services need independent scaling — which is unlikely at 100–500 users.

4.2 No real-time websocket

requirements.json explicitly states: "Leaderboard and analytics use periodic polling/sync every few minutes." No websocket or pub/sub component is added. The game timer is client-side; the backend only validates on submission. This is appropriate at launch scale.

4.3 IAP routing — digital goods policy

requirements.json monetizationType is "digital goods (store IAP required)". The level-unlock purchase (~₹49) must go through Apple App Store IAP and Google Play Billing. An external payment processor node (Stripe, Razorpay, etc.) would be an App Store policy violation for this purchase type. The backend IAP Receipt Validator service calls Apple's /verifyReceipt and Google's Purchases API to verify and record unlock status before granting access to levels 6–100.

4.4 Force-upgrade endpoint

requirements.json appStore.forceUpgrade is required. The Flutter app calls GET /v1/version/minimum at every cold launch before any other API call. If the installed build version is below the server-returned minimum, the app shows a blocking upgrade screen and prevents further interaction. The endpoint must return both minimumVersion and currentStoreVersion so the client can deep-link to the relevant app store listing.

4.5 Compliance for apps involving minors — 🛡

Verify with legal/compliance counsel The following components are included because meta.domainFlags includes "apps involving minors." Which specific regulations apply (COPPA, UK Age Appropriate Design Code, India DPDPA) depends on where users reside and how data is collected. Confirm before launch.
  • Age Gate + Parental Consent Service: sign-up collects age; users under 13 trigger a parental consent flow. Consent record stored in User.parentalConsentStatus with a timestamp. Required by COPPA-class regulation (verify with counsel).
  • Child-directed ad flag: AdImpressionLog records isChildDirected per impression. The AdMob SDK's child-directed treatment flag must be set in the Flutter client for users with ageGroup = child. Non-personalised ads only for under-13 users.
  • Audit Log Service: Immutable log of any access, export, or deletion of user data for minor accounts. Required to demonstrate compliance if queried by a regulator.
  • Account deletion: requirements.json mandates immediate data removal on in-app deletion. The deletion flow must wipe all PII and child data rows (not just soft-delete) and log the deletion event to the audit trail.
  • Privacy Policy and Terms of Service: requirements.json flags both as "needs drafting." These must be live at App Store / Play Store submission time, and the privacy policy must include child data practices. Not an agent-generated deliverable — requires human review and legal sign-off.

4.6 Admin dashboard as second client node

requirements.json discovery.platform is "mobile + web admin dashboard". v1 uses AdminJS embedded in the FastAPI app at /admin — not a custom React SPA. AdminJS connects directly to NeonDB/Postgres for CRUD on BibleCharacter, Question, Level, User, and ContentPublishRecord. Custom AdminJS actions handle content publish (§19) and leaderboard attempt invalidation (§21). CSV report export via lightweight FastAPI endpoints. Retool connected to NeonDB is an acceptable alternative if the operator prefers a hosted no-code UI.

4.7 Offline / Practice mode & content versioning

Practice mode (M-18–M-20) is offline-capable via a versioned Practice Content Pack stored on-device. Main/ranked mode (M-13) always fetches questions live from the Game Service — admin publishes are visible on the next level attempt with no cache delay.

Sync model (design-spec §19):

  • Server maintains monotonic content_version, incremented only on admin Publish content (draft edits do not affect clients).
  • On every online cold launch, mobile calls GET /v1/content/manifest after the force-upgrade check. If server.content_version > local, a background download of GET /v1/content/practice-pack runs — non-blocking.
  • Downloaded pack is checksum-verified and atomically swapped. Practice gameplay (M-19) never calls the question API — only reads the local pack.
  • App binary ships a seed pack for first-install offline play. Stale packs remain playable offline until the device reconnects.

Main mode still requires network for ads, leaderboard sync, and IAP validation. The Content Sync service builds practice packs from approved+active questions at publish time.

4.8 Data residency and hosting

requirements.json security.dataResidency states: "No strict requirement — agent to select cost-effective hosting; note COPPA/privacy obligations for minors." Railway and Render both default to US regions. NeonDB defaults to AWS us-east-1. No data-residency override is required by the stated requirements, but if the app's primary user base is India, note that storing Indian user data (including minors' data) on US servers may have DPDPA implications — verify with legal counsel. A future migration to a Mumbai/Singapore-region NeonDB branch can be done without application code changes.

4.9 Notifications — local reminders in v1; remote push deferred

v1 includes local on-device notifications via flutter_local_notifications — no FCM/APNs server, no push gateway in the backend diagram. Triggers: 3-day and 7-day inactivity nudges ("Level X is waiting!"), rescheduled on each app open. User opt-in after first level complete; toggle in Settings M-27.

Remote push (FCM/APNs) deferred post-v1 for campaign-style re-engagement. Firebase project from Crashlytics can be reused when remote push is added.

4.10 Leaderboard anti-cheat

Global leaderboard requires server-authoritative attempts (design-spec §21). Flow:

  • POST /v1/game/levels/{id}/attempts/start — server draws questions, returns attempt_id + sequence (no correct answers exposed).
  • POST /v1/game/attempts/{id}/answers — per-answer validation: sequence order, correctness, time plausibility (≥800ms/question floor).
  • Score computed server-side on 10th correct answer; LeaderboardEntry written automatically — clients have no score POST endpoint.
  • Suspicious attempts flagged and excluded; rate limits on attempt starts.
  • Phone-path abuse controls: generated app install ID + IP rate limits for account creation; no covert device fingerprinting for children.

4.11 Media uploads — not included

requirements.json backend.mediaUploads.needed is false. Launch quiz content uses text and verse clues. image_clue schema/UI is supported but image assets are not launch-blocking. If image-based question assets are added broadly post-launch, an S3-compatible bucket (e.g. Cloudflare R2) should be added as an admin-only upload path — not a user-facing upload.
